Whether the function a call names is resolved: probe/binding_matrix.sh, 2026-09-17.

Only Plan.extensions[].extensionFunction.name is rewritten. Arguments, schemas and declared output
types stay exactly as they were, so nothing here can be refused for a shape the plan no longer has.
Four rewrites, and each answer is read against the first:

  control    a partner with the same signature and the same return - add for subtract, is_null for
             is_not_null, equal for not_equal away from a join key. Every answer should be the answer
             to the original plan. A refusal here means the rewrite itself is what the participant
             objects to, and its other columns say nothing.
  mismatch   a key declared under the same URN that the call does not match: add:i32_i32 becomes
             add:i8_i8 over i32 arguments, sum:i64 becomes sum:i8 over an i64 one. The key exists,
             so looking it up succeeds; only checking it against the call can fail.
  signature  add:dec_dec becomes add:str_str: the short name stands, the argument types in the
             compound name do not. A refusal means the key as a whole is checked. An unchanged
             answer means the short name is resolved some other way, not that nothing is resolved.
  unknown    the short name becomes one no extension file declares. A refusal means names are
             resolved at all; an unchanged answer means the call is carried through unbound.

The control covers 18 of the 42 cases that declare a function. multiply and divide have no partner
returning the same type, and a case whose swapped anchor is referenced from a join key is left out:
Acero accepts only equal or is_not_distinct_from there, and the substrait-java Spark path has no
conversion for not_equal, so swapping one would refuse for a reason that is not about binding. The
rewrite is per declaration and a declaration is shared by every call that references it, which is
why that exclusion is per case rather than per call.

mismatch reaches eight cases. An alternative signature has to be declared in the same extension file
or the key would simply be absent, which is the unknown column again, and only add:i32_i32, avg:i64
and sum:i64 have one. sum is the useful one twice over: sum:i8 returns the i64? that sum:i64
returns, so the declared output type still agrees with the key and a refusal there could only be
about the arguments.

Nothing refuses the mismatch. Every participant accepts sum:i8 over an i64 argument and add:i8_i8
over i32 ones, including the three that refuse a key they cannot find. Looking the key up and
checking it against the call are different things, and only the first is done anywhere here.
Isthmus's count of unchanged answers is lower than the rest for a reason that is not a changed
answer: three of its nine cases refuse in both corpora with a message that prints the function name,
so the text moves when the name does.

Four behaviours on the other columns, and the control is clean for all nine.

substrait-java, Isthmus and Spark look the compound key up in the loaded extension and refuse both
rewrites alike: "Unexpected scalar function with key add:str_str. The URN ... is loaded but no
scalar function with this key was found."

DuckDB, DataFusion and Acero resolve the short name against their own registry rather than against
the declaration. add:str_str binds, because add is one of their own; no_such_function does not.

substrait-python resolves nothing and says nothing: it answers every rewrite with the schema it
answered the original with, and prints no diagnostic at all.

The validator does not distinguish the rewrites either, but it is explicit about why, in both of its
configurations. As the probe runs it, with URN resolution off, every case carries "did not attempt to
resolve YAML: configured recursion limit for URN resolution has been reached (code 2001)". With
URN_DEPTH set it finds the extension file and reports "not yet implemented: the following child nodes
were not recognized by the validator: description, impls, name (code 0001)", and returns the same
schema for the original and for a name no file declares. So the validator is not measured on this
question rather than answering it permissively: at the pinned revision it says it has not implemented
the check, and its schema output has to be read beside that diagnostic.

substrait-go is not measured on signature and unknown. It parses the compound name's suffix as a
type string and fails there - "mismatched input 'str' expecting {'IF','FUNC','BOOLEAN','I8',...}" -
before any lookup, and on the unknown corpus it fails the same way on 'dec'. Those two counts
describe that parse, not binding, and are left in the table rather than removed so the next reader
does not take them for an answer. Its mismatch column parses and is measured.

Read beside results/LIE.txt: of the five participants whose answer follows a swapped output type,
two - substrait-python and the validator - never resolve the function either, so their schema comes
from the plan and nothing else. substrait-java and Isthmus check the name and still take the type
from the plan.
